# Architectural Decisions

D-1 to D-3 cover the repository bootstrap. D-4 onward are the approved V1
engine design. They are frozen unless a concrete correctness issue is
discovered, and are not yet implemented. Full design:
[architecture.md](architecture.md), "Engine Architecture". Project state:
[docs/progress.md](progress.md).

## D-1 Modular monolith for V1, not microservices

**Decision:** Parallax V1 is built as a single deployable Spring Boot
application with a framework-independent engine module, not as a set of
separately deployed services.

**Why:** V1 scope is one instrument, long-only, daily bars, a single
research application. There is no independent scaling, deployment, or team
boundary that would justify the operational cost of microservices (service
discovery, network calls between services, distributed transactions,
independent deployment pipelines). Introducing microservices now would add
infrastructure complexity without solving a real problem, and would work
against reproducibility by adding more moving parts and network boundaries
that could introduce nondeterminism.

**Consequence:** The engine is still kept architecturally independent of
Spring (see [architecture.md](architecture.md)) so that a future move to a
separate service, if ever justified, would not require rewriting core
backtesting logic. Independence is enforced through Maven module boundaries
today, not through a network boundary.

## D-2 Root Maven aggregator with `engine` and `backend` as modules

**Decision:** A root `pom.xml` at the repository root aggregates `engine`
and `backend` as Maven modules. The root POM has `packaging=pom` and is not
itself a Spring Boot application.

**Why:** This allows `engine` and `backend` to be built and tested together
with a single Maven invocation from the repository root, while keeping
`engine` a plain Java module with no Spring dependency. The `backend` module
keeps `spring-boot-starter-parent` as its own Maven parent for Spring Boot's
dependency management; Maven module aggregation does not require a child
module's `<parent>` to be the aggregator POM, so this does not conflict with
Maven's single-parent rule.

## D-3 Maven wrapper moved to repository root

**Decision:** The Maven wrapper (`mvnw`, `mvnw.cmd`, `.mvn/`) generated by
Spring Initializr under `backend/` was moved to the repository root.

**Why:** With a root aggregator POM, the whole multi-module project (engine
+ backend) should be buildable from a single location with a single
wrapper invocation: `./mvnw clean install` from `C:\Parallax`. Keeping the
wrapper under `backend/` only would suggest the backend is the root of the
Java build, which is no longer true. There is no concrete reason to keep a
second wrapper under `backend/`, so it was not duplicated.

## D-4 Invalid market data fails fast; no provider logic in the engine

**Decision:** `Bar` and `BarSeries` validate on construction (positive
prices, consistent high/low, non-negative volume, non-blank symbol,
non-empty series, strictly ascending dates). Invalid data is rejected
before the run starts. Bars are never reordered, deduplicated, repaired,
clamped, or skipped. Market-data providers and normalization live in the
backend; the engine receives a validated `BarSeries`.

**Why:** Repairing data inside the engine would silently invent financial
assumptions. Rejection is deterministic and visible.

## D-5 Stateless Backtester, single-pass loop, metrics outside the loop

**Decision:** `Backtester.run(series, strategy, config)` holds no persistent
fields; each run creates its own mutable state (`Portfolio`, indicators,
pending order, result lists). Processing is single-threaded and
single-pass. Metrics are computed afterwards by `PerformanceMetrics.of(result)`.
No event bus, broker model, order book, or other speculative
infrastructure.

**Why:** A fixed-order loop is the smallest structure that can be read top
to bottom and verified for look-ahead bias. Keeping metrics out of the loop
separates simulation from analysis.

## D-6 Inclusive date range with separate lookback

**Decision:** `BacktestConfig` has inclusive `startDate` and `endDate`.
Bars before `startDate` are lookback bars: they update indicators and do
nothing else (no signals, orders, fills, or equity points). Bars after
`endDate` are ignored. There is no lookback-count field; the lookback is
whatever the supplied series contains before `startDate`. `BarSeries`
itself knows nothing about the range.

**Why:** Indicators can be warm at `startDate`, so strategy activity is not
delayed by warm-up inside the requested range, and the first in-range
equity point equals initial capital.

**Consequence:** Results depend on where the supplied series begins (EMA
and RSI seeding), so the supplied lookback is part of reproducibility
(D-15).

## D-7 Sizing at bar N close; execution at N+1 open; whole-order rejection

**Decision:** A signal at bar N close sizes a BUY using only N-close
information: `floor((cash × fraction − commission) / (close_N × (1 +
slippageRate)))`. Quantity ≤ 0 is recorded as a `ZERO_QUANTITY` rejection
and no order is created. The order executes at the next available bar's
open. If `quantity × fillPrice + commission` exceeds available cash, the
entire order is rejected (`INSUFFICIENT_CASH`); quantity is never reduced
and there are no partial fills. SELL orders sell the full held position.

**Why:** The decision and the quantity use only information known when the
order is placed. The N+1 open is used only for execution. A single
deterministic rejection rule is simpler and more honest than silently
resizing orders.

## D-8 Range boundaries: no signal on the last in-range bar, no fills outside the range, no forced liquidation

**Decision:** The strategy is not evaluated on the last in-range bar, so
no order is ever pending at the end of the run and no fill occurs outside
`[startDate, endDate]`. If `endDate` is a non-trading day, the last
available in-range bar is used. An open position at the end is marked to
the last in-range close, not liquidated. A request with no in-range bar is
rejected before execution.

**Why:** Liquidating would require a price outside the execution rules,
and filling after `endDate` would let bars outside the requested range
affect results.

## D-9 Market orders only in the first implementation milestone

**Decision:** Only market orders executed at the next available bar's
open. Limit and stop orders are excluded.

**Why:** CLAUDE.md V1 scope lists market orders. Limit/stop orders need
intrabar high/low fill rules, which are a separate correctness problem.

## D-10 Structured strategies without a general expression language

**Decision:** `StrategyDefinition(entry, exit, sizing)`. Conditions are
`Compare` (`GT`, `LT`), `All`, `Any`. Operands are `IndicatorRef`,
`Constant`, `Close`. The only sizing mode is `CashFraction(0 < f <= 1)`.
The strategy sees only an `IndicatorSnapshot` as of N close, and only once
every referenced indicator is ready. Entry is evaluated when flat, exit
when long.

**Why:** Expresses the V1 examples as data with no user code. No `NOT`,
arithmetic, equality, `>=`/`<=`, or crossover abstractions until needed.

## D-11 Indicators are per-run incremental objects fed one close at a time

**Decision:** One runtime `Indicator` per distinct `IndicatorSpec`, with
`update(BigDecimal close)`, `isReady()`, `value()`. Indicators never see
the `BarSeries`. SMA(n) and EMA(n) are ready after `n` closes (EMA seeded
with SMA); RSI(n) uses Wilder smoothing and is ready after `n + 1` closes;
RSI is 100 when `avgLoss = 0` and `avgGain > 0`, and 50 when both are 0.

**Why:** An indicator that only ever receives past closes cannot leak
future data.

## D-12 Fills are the source of truth; SignalEvent is carried by Fill; trades are derived

**Decision:** Every `SignalEvent` has exactly one outcome: a `Fill` or an
`OrderRejection`, each carrying the `SignalEvent`. Orders are transient and
not part of the result. No separate signal list and no mutable open-trade
tracker exist. Trades are derived after the run from alternating BUY/SELL
fills; a trailing BUY is an open trade marked to the final close and is
excluded from completed-trade statistics.

**Why:** One record of execution history, with the explanation for each
trade attached to it, avoids duplicate state.

## D-13 Average-cost accounting with commissions in cost basis

**Decision:** `Portfolio` owns cash, quantity, cost basis (including buy
commissions) and realized P&L, and is mutated only by applying fills. SELL
removes `costBasis × q / currentQuantity`; proceeds are net of commission.
Unrealized P&L and equity are derived at a close; average cost is derived
for display only. The identity `equity = initialCapital + realizedPnl +
unrealizedPnl` is tested at every in-range equity point.

**Why:** Realized P&L is net of all trading costs, and the identity catches
accounting drift.

## D-14 BigDecimal ledger values, double indicator values

**Decision:** `BigDecimal` for prices, fill prices, commissions, slippage
rate, cash fraction, cash, cost basis, P&L, equity and initial capital;
compared with `compareTo`; not rounded to cents inside the engine; a fixed
`MathContext` for the partial-basis division if required. `long` for
quantities; `int` for periods and order IDs; `double` for indicator
calculations, indicator outputs, condition comparisons and later derived
statistics.

**Why:** Ledger values must reconcile exactly. Indicators and statistics
are approximate by nature, and Java floating point is deterministic.
Not to be redesigned during early implementation without a concrete
correctness problem.

## D-15 Determinism and reproducibility requirements

**Decision:** Identical `BarSeries` content, `StrategyDefinition`,
`BacktestConfig` and engine version produce identical results. The engine
avoids current time, randomness, static mutable state, order-affecting
parallelism, hash-order-dependent behavior and locale-sensitive behavior.
Order IDs are sequential; indicator creation order is deterministic.

**Consequence:** Experiment persistence must eventually identify the exact
supplied series, including its lookback portion, not just the requested
date range.

## D-16 Long-only, no leverage, no Instrument abstraction

**Decision:** One long position at a time, whole shares, no leverage, no
pyramiding, no partial strategy exits, no multiple simultaneous positions.
The instrument is identified by the `BarSeries` symbol only.

**Why:** V1 scope in CLAUDE.md. An Instrument type would carry metadata V1
does not use.
